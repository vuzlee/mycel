Outbox: a committed job is never lost on its way to the queue

Saving a row and sending a message are two writes to two systems. A crash between them loses the job.

01 Problem02 Components03 Inside the code04 When things go wrong 05 Three moves06 Guarantees and limitsImplementation

01 · The problem

Without an outbox: the API saves the document, then dies before it publishes.

Postgres
document saved · pending
API
commit
✕ dies before publish
Queue
no job ever arrives
crash between two writes
The row says "pending" forever; no worker knows it exists

Key: a database commit and a broker publish cannot be one atomic step. One of them must be made recoverable.

04 · When things go wrong

Four failures, each from the code above.

What happenedWhat the relay checksResult
Abroker down while the request publishesrow unsent after 10 s → publish on the next tickdelivered late
BAPI dies after commit, before publishsame row, same pathdelivered late
Cpublished, but marking failed or the relay died after publishrow still unsent → published againsent twice the worker's safeguards absorb it
Da row holds a job kind this build no longer knowscannot be read → log error, mark sent, move ondropped logged, never blocks the queue head

Key: the outbox trades "maybe lost" for "maybe twice". Twice is cheap; lost is not.

05 · Three moves

Each answers one question.

1 stageWhere does the job live until it is sent?in the caller's transaction, beside its data
2 sendCan it go out right now?yes, usually; failure is logged, not raised
3 relayWhat if send never happened?a timer republishes old unsent rows, one per transaction

06 · Guarantees and limits

Guaranteed

  • A job exists exactly when its data was committed.
  • A committed job is published at least once, if the relay keeps running.
  • Two relays never take the same row at once.
  • A relayed job keeps the request's trace context.

Not guaranteed

  • Exactly once. A crash between publish and mark sends it twice.
  • Speed on failure: up to 10 s wait plus one 5 s tick, longer behind a 100-row backlog.
  • An unreadable row is dropped with a log line, not retried.
  • Nothing runs if the scheduler is down; rows wait.

Key: delivery is at least once on purpose; the duplicate is the consumer's job to absorb.
