Idempotency: a job delivered twice is answered once

The queue may hand the same question to a worker more than once. Each extra run costs a model bill.

01 Problem02 Components03 Inside the worker04 When things go wrong 05 Four safeguards06 Guarantees and limitsImplementation

01 · The problem

Without safeguards: worker A dies mid-answer, the queue hands the same job to worker B.

Queue
job 42
job 42 again
Worker A
calling the model…
✕ dies
Worker B
calls the model again
no ack → redelivered
Same question answered twice → two model bills, two answers streamed into one chat

Key: the queue (RabbitMQ) promises at least once, never exactly once. The worker must cope with repeats.

05 · The four safeguards

All four run inside the worker, in the order shown in the 02 table. They are not four ways to stop duplicates: each answers a different question.

1 COUNTHas this job crashed workers too often?stops D · a poison job looping forever
2 DONE?Has this job been answered?stops B · reuses a saved answer
3 LOCKIs someone answering it right now?stops A · two workers at once
4 ONE ROWIf two writes happen, where do they go?one row per job id; last write wins. Does not stop a model call

06 · Guarantees and limits

Guaranteed

  • A saved answer is not recomputed.
  • A repeat never creates a second turn row.
  • A job that keeps killing workers stops after 4 deliveries.
  • A worker only renews or releases its own claim.

Not guaranteed

  • Exactly once. A crash before save (story C) runs the model again.
  • DONE? is checked before the claim. If A saves and releases between B's check and B's claim, B runs again.
  • A lost claim (Redis unreachable > 25 s) only logs a warning; the work goes on, and a second worker may start. No fencing token guards the save.

Key: the model is called twice only when no answer was saved in time, or in the two narrow races above.
