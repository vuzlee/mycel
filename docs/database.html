01 · The layers

Raw in, contract out

02 · Identity

Two kinds of key, never interchangeable

Primary key

Issued by PostgreSQL. Addresses a row, means nothing outside this database — copy the data elsewhere and the numbers differ.

Natural key

Issued by the source: (source, issue_key) in work_item, (source, worklog_id) in worklog. An edited issue keeps it, so a re-sync updates the row instead of appending a second opinion.

source belongs in the key because Jira will not be the last tracker, and PROJ-12 is a name anyone can mint. The bronze tables are the exception: Jira's own id is already unique and serves as the primary key directly.

No foreign keys link the layers. Deliberate — each layer must be rebuildable on its own, from the layer below.

NULL means something here, it is not missing data. The older rule was that every column is NOT NULL, because a nullable column becomes an if branch at every read site. An issue tracker breaks that rule legitimately: unassigned, unestimated, no due date and not resolved are real states of real work, and coercing them to 0 would be a lie. Columns that are always present — keys, kind, status, title, the sync timestamps — stay NOT NULL.

03 · bronze

Written once, never edited

bronze.jira_issue

Written by domains/sync.py, read by etl/. The payload goes down before anything is parsed, so whatever the normaliser gets wrong today can be re-run against this table tomorrow without calling Jira again.

issue_id varchar(32) Jira's internal id. The primary key rather than the issue key, because renaming a project rewrites every key and leaves the ids alone. 10042
issue_key varchar(64) The name people read. Lifted out of payload so a lookup needs no JSON access. MYC-12
payload jsonb The whole issue. jsonb, not text: PostgreSQL parses on write, so it can be queried in place — payload->'fields'->>'summary'. {"id":"10042","key":"MYC-12","fields":{…}}
fetched_at timestamptz · now() When we pulled it — not when the issue changed. That moment lives in gold.work_item.updated_at. Filled by the database. 2026-09-21 07:14:02+07
PRIMARY KEY (issue_id)
bronze.jira_worklog

A separate table because it is a separate API call, paged separately, that fails independently of the issue it belongs to.

worklog_id varchar(32) Jira's id for the logged entry. 10307
issue_key varchar(64) Which issue the hours were logged against.
payload jsonb The entry, verbatim.
fetched_at timestamptz · now() When we pulled it.
PRIMARY KEY (worklog_id)

04 · silver

The same columns, a different obligation

silver.work_item · silver.worklog

Column for column identical to their gold counterparts below, natural keys included, so this page does not list them twice. Read section 05 and you have read both.

UNIQUE uq_silver_work_item_natural_key (source, issue_key)
UNIQUE uq_silver_worklog_natural_key (source, worklog_id)
INDEX ix_silver_work_item_project_updated · ix_silver_work_item_due_at · ix_silver_worklog_project_started

Identical is the expected state, not a duplication to clean up.

  • Silver answers to the source. Jira adds a field, renames a status — this table changes.
  • Gold answers to the question. A new dashboard block — that table changes.
  • One source, one sentence. Both describe the same table today, so etl/promote.py is the identity function.
  • What it buys: a place for the difference when a second tracker arrives.
  • What it costs: every sync writes each row twice.

silver.message was dropped by migration 0005. Empty since batch 016 removed its source. An unwritten table beside a live layer is a standing question about which of the two is real.

05 · gold

The only layer agents read

gold.work_item

One issue, one row. A contract: adding a column is free, changing what an existing column means takes two releases, because the report, the dashboard and the calendar writer all read it.

id serial Internal row address. Not stable across databases — do not expose it.
source varchar(32) Which tracker. jira
issue_key varchar(64) The issue's name. Retitling, restatusing and logging hours all keep it, so the next sync is an UPDATE rather than a second row.
project varchar(32) · indexed One project is one team; every query starts here. Stored rather than derived from the key, because an index on a column is cheaper than one on a substring expression. MYC
issue_id varchar(32) Points back at the bronze row.
kind varchar(16) The issue type, normalised. Every Jira site names its own types, so "Story" here and "User Story" there have to become one word before gold. epic · story · task · subtask
parent_key varchar(64) · nullable The hierarchy, held as a key rather than a foreign key: a sync can fetch a child before its parent, and an FK would fail a transaction over an accident of ordering. NULL on an epic, which has no parent. MYC-3
title text The summary, verbatim. text has no length limit and is no slower than varchar in PostgreSQL.
status varchar(64) The site's own name for the status, untranslated. A team that calls it "Đang review" should read that word in its report. In Progress · Đang review
status_category varchar(16) Jira's own three-way grouping. This is what counts and compares across sites; status does not. todo · doing · done
assignee_account_id varchar(128) · nullable Since 2019 accountId is the only identifier Jira supports — username and email were removed from the API for GDPR. This is what to group by. 557058:9f1a…
assignee_name varchar(128) · nullable Display only, and it can change. Grouping by it splits one person in two the day they edit their profile.
original_estimate_seconds bigint · nullable In seconds, because that is the unit Jira stores. Converted to days only for display, in services/analyze.py and Dashboard.tsx — a conversion in the warehouse is a rounding nobody can undo. 28800 = one 8-hour day
time_spent_seconds bigint · nullable Jira's own total of logged work. The difference between this and the line above is the number the dashboard exists to show.
due_at timestamptz · indexed · nullable The deadline. Indexed because "what is overdue" runs on every dashboard load, and it is the only column that leaves for Google Calendar.
created_at timestamptz Stamped by Jira at the moment of the API call, so wrong for anything entered after the fact. Recorded because it is free; no chart is drawn from it.
resolved_at timestamptz · nullable The same problem, worse: a back-filled project produces one tidy, entirely fictional day on which everything shipped. Effort curves come from worklog.started_at instead.
labels jsonb An array of strings, kept as-is. Nothing filters on it yet — kept because collecting it costs nothing now and a full re-sync later.
updated_at timestamptz · indexed When Jira last recorded a change, not when we wrote the row. This is the sync's high-water mark: the next JQL asks updated >= this, so only what moved comes back.
PRIMARY KEY (id)
UNIQUE uq_work_item_natural_key (source, issue_key)
INDEX ix_work_item_project_updated (project, updated_at)
INDEX ix_work_item_due_at (due_at)
gold.worklog

One logged entry, one row. This is what turns effort into a curve over days rather than a single running total sitting on an issue.

id serial Internal row address.
source varchar(32) As above, for the same reason.
worklog_id varchar(32) Jira's id for the entry. Editing an entry keeps it, so a re-sync is an UPDATE.
project varchar(32) · indexed Copied down from the issue so a chart needs no join. Indexed together with started_at — the shape of the question "this project, this week".
issue_key varchar(64) Which issue the hours went to.
author_account_id varchar(128) · nullable Who logged it — accountId again, not a name.
author_name varchar(128) · nullable Display only.
time_spent_seconds bigint Seconds, for this entry alone. Summed by day it is a chart; summed by person it is load.
started_at timestamptz · indexed The one time field that can be back-dated honestly. The person logging declares "these hours were Tuesday" and Jira records exactly that — unlike created dates and status transitions, which are stamped at the moment of the API call. Everything time-shaped in a report goes through this column.
comment text · nullable What the person wrote, if anything. Usually the only sentence saying why it took that long.
PRIMARY KEY (id)
UNIQUE uq_worklog_natural_key (source, worklog_id)
INDEX ix_worklog_project_started (project, started_at)

The accepted values for kind and status_category live in etl/normalise.py. The database itself accepts any string of the right length — there is no CHECK constraint yet.

What migration 0004 dropped. gold.progress_update and bronze.telegram_message were removed rather than deprecated. They held the output of a hashtag convention — #done, #wip, #blocked at the front of a chat message — which made a person do the parser's job and still could not say what a task was estimated at, when it was due, or which epic it belonged to. Keeping a table nothing writes to keeps an open question about which one is real.

No status history. GET /issue/{key}/changelog would give transitions, but it costs one request per issue and returns timestamps that cannot be back-dated. So Mycel does not ask, and nothing downstream claims to know how long an item has been sitting in a status.

06 · app

Product data, not pipeline data

Four tables from migration 0002: app.user and app.session for who is signed in, app.conversation and app.report for what they have run. A report's body is jsonb — that is what lets an agent's output schema change without a migration, and it is exactly why batch 017 could replace the summary's shape without touching this table.

A separate schema, on purpose. The medallion grant — agents get SELECT on gold and nothing else — should not accidentally hand them session tokens and password hashes. Product data sitting in its own schema does not inherit a pipeline grant.

app.user

Someone who can sign in.

email varchar(254) · unique The identity itself. No separate username: two names for one person is two things to keep in step for no gain.
password_hash text Argon2id. No plaintext exists anywhere, not even in transit through the model class — services/auth.py hashes before constructing one.
app.session

One browser, signed in, until it expires or signs out.

id varchar(64) The cookie value itself: 32 random bytes, hex-encoded. Not a JWT — revoking one needs a server-side list of the revoked, which is this table with extra steps.
expires_at timestamptz Checked on read, enforced by nothing. A session one second past expiry must read as gone before any sweeper runs. 14 days
last_seen_at timestamptz Touched on every valid request. Nothing reads it yet.
app.conversation · app.report

One thread in the sidebar, and one finished run kept beside it.

conversation.kind varchar(16) Separates the two product surfaces — a free-form chat and a progress summary. Different pages, and only one of them has a chat to speak of.
report.conversation_id int · on delete cascade Forgetting a thread in the sidebar forgets every run under it. The cascade is why DELETE /conversations/{id} needs no second step.
report.job_id varchar(64) · unique A redelivered job updates its row instead of writing a second one.
report.spent_usd numeric(12,6) Not a float. These numbers are added up and reported; binary floating point does not hold a decimal value exactly.

Redis and app.report coexist. Redis holds a result for result_ttl_seconds so a second process can read it — a holding area, always described as one. This is the record. Redis answers is it done yet; this answers what did we produce last week.

Expired sessions are not swept. AppRepository.delete_expired_sessions exists and nothing schedules it. An expired row is deleted the moment someone reads it, which is enough while the cookie is dead either way.

07 · Reading the columns

Timestamps that look alike

PairDifference
fetched_at / updated_at When we pulled it / when Jira recorded the change. The second is the next sync's high-water mark; the first is only for forensics.
resolved_at / worklog.started_at The pair that matters most. Jira stamps resolved_at at the moment of the API call, so a back-filled project has one day on which everything finished. started_at is declared by the person logging, so it can be back-dated — which is why every time-shaped chart is drawn from worklogs.
time_spent_seconds, in two tables On work_item it is Jira's total for the whole issue. On worklog it is one entry. Summing the second by issue gives the first — unless someone overrode it by hand, in which case Jira's own total wins.
id / natural key Our row number / the source's ids. Only the second survives a rebuild.

Why each type was chosen

09 · Operations

Applying and rebuilding

uv run alembic upgrade head   # create everything
uv run alembic current        # → 0004 (head)
uv run alembic downgrade base # drop everything

A migration file is a description, not an action. It does nothing until upgrade runs. A fresh container, or a dropped volume, needs upgrade head again.

Not seeing the tables in a DB client? Check which schema is open. Clients default to public, which holds only alembic_version.
