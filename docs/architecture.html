Mycel

A multi-agent system that assembles reports and dashboards from scattered data sources. Named after mycelium — the underground fungal network connecting a whole forest: running in the background, quietly gathering data, and only then surfacing as a report.

Part 1

The idea

Data from scattered sources flows one way through four layers and ends as a report. Understand this part and you understand what the system does.

1.1 · Data flow

Data flows one way through four layers

Each layer only reads the layer directly below it and writes to the one directly above. No shortcuts: agents never touch raw or silver.

This is the data axis, not the request axis. The flow sources → raw → etl → silver → gold runs in the background on a schedule, measured in minutes. When a user presses a button the request takes a different axis — controller → pipeline → service, measured in seconds. The two meet in exactly one place: at gold. Part 2 covers the request axis.

1.2 · The contract between layers

Why raw is kept untouched

When transform logic is wrong — and it will be — it can be re-run from raw instead of calling the provider again. Providers have rate limits, deleted data, and APIs that change schema. raw is the copy we control.

Part 2

Code flow

Which layers a request passes through, which layer calls which, and which module may import which.

2.1 · Each layer's responsibility

Who does what in a request

HTTP does not call services directly. It enters managers/ — one directory per business domain, holding a controller that receives the request and a pipeline that wires services together.

Layer May May not
api/app.py Create the app, mount each manager's controller, middleware, observability Hold endpoints · hold business logic
managers/·/controller.py Receive the request, validate, call the pipeline, return the response SQL · call an LLM · business if/else
managers/·/pipeline.py Define the order of the steps, calling services in turn Do a service's work · know whether it was called from HTTP or cron
services/ One single job, done end to end, reusable across pipelines Chain other services together — that is the pipeline's job
etl/ agents/ reports/ The heavy lifting: transforms, reasoning, artifact building Read the HTTP request · write SQL by hand
storage/ Every SQL statement, session and transaction Hold business decisions

How a pipeline differs from a service: the pipeline is the chain, a service is a link. managers/report/pipeline.py calls, in order, permission → queue → gather → analyze → render. managers/sync/pipeline.py calls fetch → transform → check. Services are reused by both; a service itself does not know which chain it is in.

2.2 · The life of a request

From the button press to the finished report

Producing a report takes minutes and will sometimes fail halfway. So the API does not run it — it pushes the work onto the queue and returns immediately. The whole path is one trace.

2.3 · Dependency order

Dependency order

Arrows read as “is imported by”. No arrow points back upwards — if you find yourself needing an upward import, the design is wrong somewhere.

Part 3

Directory layout

One job per folder, obvious from the name. The last section goes deep into the AI layer — the easiest place to get wrong.

3.1 · Directory layout

The name tells you the job

Modules are flat, one level deep. When a module outgrows a file it becomes a directory with the same name: sources/slack.py → sources/slack/{client,parser}.py. No abstraction layer is built before there is anything to put in it.

Source
src/mycel/
├─ core/ Config, logging, exceptions, shared types. The bottom layer — imports no other module.
├─ storage/ Three stores, three kinds of data. Every access goes through here — not scattered through pipelines and agents.
│ ├─ storage/postgres/ Transactional state: engine, session, a repository per raw · silver · gold layer. Every SQL statement lives here.
│ ├─ storage/vectors/ Knowledge base search over embeddings (Qdrant). Embeddings come from gold, not raw. View permissions are a Qdrant filter, not a post-filter after top-k.
│ └─ storage/objects/ Large files: source PDFs, rendered reports (MinIO, S3 API). Postgres holds the metadata, the bucket holds the content. The API returns a presigned URL so files never pass through the API process.
├─ sources/ One file per provider. Same interface: take a time range, return raw records, write to raw.
├─ etl/ The raw → silver → gold transform steps. Scheduled background work — not the request-handling chain. Every step is idempotent.
├─ etl/checks/ Validation after each step: missing columns, unexpected nulls, row counts off. On failure it stops and does not write to the layer above.
├─ llm/ The only gateway to any model. router picks local or cloud, client is the only place that imports a provider SDK, cache avoids repeat calls, tokens/usage count before and after, budget blocks going over the ceiling.
├─ agents/ orchestrator coordinates; analyst · writer · reviewer do one job each; tools/ are the capabilities an agent can call (query_gold for exact-number questions, search_docs for vague ones); prompts/ is kept out of the code so edits need no redeploy.
│ └─ agents/core/ The shared foundation for agents/ alone, with no business logic: the agent loop, streaming/, hooks (attach traces · log usage · add to budget), guards, integrations/mcp.
├─ queue/ The job layer on top of Kafka (the broker runs outside, KRaft mode). Kafka is an ordered log, not a task queue, so this is built by hand: tiered retry topics jobs → jobs.retry.1m → jobs.retry.10m → jobs.dlq, retry counts in the header, a raised max.poll.interval.ms. Commit after the job finishes ⇒ at-least-once ⇒ an idempotency key is mandatory. The way in is services/enqueue.py.
├─ managers/ Entry points, split by business domain. Adding a domain = adding a directory, with existing domains untouched.
│ ├─ managers/report/ The report domain: controller.py (HTTP endpoints) · pipeline.py (the business chain) · schemas.py.
│ └─ managers/sync/ The sync domain: the same three files, for the fetch → transform → check flow.
├─ services/ Single links, one job per file: permission, enqueue, fetch, transform, gather, analyze, render, check. Names are verbs with no _service suffix. Reusable across pipelines.
├─ reports/ Builds the final artifacts from agent output: prose, data tables, dashboards.
├─ scheduler/ Answers when to run. Calls pipeline in managers/ directly — the same place controllers call, just without the HTTP link.
├─ api/ The HTTP shell, as thin as possible. Business endpoints live in managers/; this only assembles them. There is authentication — the data is internal Slack and Gmail.
│ ├─ app.py The assembly point: create the app, mount each manager's controller, middleware, observability. The only file that knows which domains exist. uvicorn points here.
│ ├─ middleware.py Only request_id — tracing, CORS, errors and rate limiting all use what already exists. Written as pure ASGI, not BaseHTTPMiddleware (which buffers the response and blocks SSE).
│ ├─ dependencies.py What controllers declare via Depends(): authentication, DB session, pagination. Authentication lives here rather than in middleware — it reaches the OpenAPI schema and mypy can check it.
│ └─ health.py /health/live for the container restart policy, /health/ready for the load balancer. Belongs to no business domain.
└─ observability/ tracing sets OTel up and exports OTLP, llm_trace attaches LLM attributes to spans (readable by Langfuse), logging prints JSON to stdout (Promtail ships it to Loki), metrics feeds Prometheus. Three signals, three questions: metrics is something broken, traces where, logs why — joined by trace_id appearing in all three. It knows nothing about HTTP, so scheduler and queue can import it too. Every layer calls into it.
Operations
.github/workflows/ CI runs on every PR; builds an image tagged by commit SHA on main.
evals/ The golden set that scores report quality. A prompt or model change that drops the score blocks the merge.
deploy/ Infrastructure config: otel/ (collector · Tempo · Prometheus · Loki · Promtail), grafana/, Postgres init, inference/ for vLLM, envs/, and the cluster deployment side: kubernetes/ · helm/ · argocd/ · registry/.

migrations/ Alembic. Every schema change is a revision; the DB is never edited by hand.
docs/ Design documentation — including this page.
tests/ Code tests, mirroring the structure of src/mycel/. Report quality is evals/’s job.
scripts/ One-off operational scripts. Not a place for business logic.

3.2 · The AI layer

Local carries the volume, cloud does the reasoning

Every model call goes through llm/ — no module imports a provider SDK directly. That way switching models, adding a cache or setting a spend ceiling is one change.

Part 4

Running for real

Docker, observability, and the path from dev machine to cluster. With a clear line between what exists and what is still only design.

4.1 · The operational stack

The operational stack

One docker compose up brings up both the app and the observability layer. Add --profile local-llm to run the 3B model on the machine itself. This is the dev machine stack — on a cluster the same image runs through Helm, see the next section.

api Front door

Takes report requests, returns finished results, health checks for the load balancer.

scheduler The clock

Pushes work onto the queue when the time comes. It does not execute anything, so its death loses no jobs.

worker The hands

Pulls jobs and runs them: syncs, transforms, report generation. --scale worker=N, but pods beyond the partition count sit idle.

kafka Job queue

KRaft mode, no Zookeeper. The partition count is the parallelism ceiling; it can be increased but not decreased.

qdrant Vector store

Knowledge base search over embeddings. Kept out of Postgres so it scales independently.

minio Object store

Large files over the S3 API: source PDFs, rendered reports. Moving to real S3 is just an endpoint change.

vllm Model local

Optional, enabled with the local-llm profile. Without it every call goes to the cloud.

postgres Data store

One database, three schemas. A separate volume so upgrading the image does not lose data.

otel-collector Collection point

The app sends OTLP to one place; the collector routes it to Tempo and Prometheus.

tempo Trace storage

One report request is one trace: from HTTP, through the gold query, down to each model call.

prometheus Metrics storage

Sync latency, record counts per layer, tokens and cost per model, job failure rate.

loki Log storage

Answers why it broke: stack traces, the payload the provider returned. Joined to traces by trace_id.

promtail Gom log

Reads container stdout and ships it to Loki. The app only prints JSON and does not know Loki exists.

grafana The screen

Dashboards and datasources, provisioned from deploy/grafana/ so they are versioned with the code. Click from a metric to a trace, from a trace to logs.

4.2 · From dev machine to cluster

One image, three environments

CI builds the image once, tagged by commit SHA. Staging and prod pull that exact image and run it — no rebuild, so there is no “works on my machine”.

Environment Data Model Difference
dev Personal machine, real or sample data local vLLM if there is a GPU Runs from source, hot reload
staging Anonymised Cloud, its own rate-limited key Same image as prod, different environment variables
prod Real, postgres with backups Cloud, key production Only deploys SHA tags that passed staging

All three environments run the same image. Every difference is an environment variable: the DB connection string, API keys, whether vllm is enabled. Secrets are always read from env — never from a committed config/.

4.3 · On the cluster

Kubernetes on-premise

The whole system runs in-house, with no dependency on a cloud service beyond the final LLM call. docker-compose.yml is the dev machine's stack; deploy/helm/ is the cluster's. Two different files, but the same image and the same set of environment variables — there is no if env == "prod" branch in the code.

Requirement Solution Easy to get wrong
The API can scale Deployment.replicas — many pods behind one Service —
A dead pod comes back kubelet restarts the container; the Deployment recreates a lost pod A hung pod with an open port looks healthy to K8s. Self-healing is only correct when the probes are
More traffic adds pods HorizontalPodAutoscaler api on CPU, but worker has to scale on Kafka consumer lag — it waits on I/O, so CPU stays low while the queue backs up
Services can reach each other Service — one stable DNS name, load-balanced already —
Reproducible deploys Helm — a versioned chart; the same chart + values-prod.yaml gives the same result version is the chart's, appVersion is the image's commit SHA. Rolling back the chart does not roll back the code
Automated deploys Argo CD — git is the source of truth; Argo compares the cluster to git and pulls it into line prune deletes resources no longer in git: one wrong line in values loses Postgres's PVC
Private container images Harbor — an internal registry with CVE scanning, image signing and a proxy cache Tag = commit SHA, never latest: two pods with the same manifest would run different code

Three probes, three different questions. readinessProbe decides whether it takes requests (on failure it is pulled from the Service, the pod stays alive), livenessProbe decides whether it restarts, startupProbe delays the other two during boot. Without the last one vllm is killed unfairly because loading the model takes minutes — forever.

worker’s hard ceiling: actual running pods = min(replicas, partition count). With a 6-partition topic, an HPA pushing to 10 pods still leaves only 6 with work, so set maxReplicas to the partition count. vllm does not autoscale at all: each pod holds a GPU, and with none free a new pod only sits Pending.

scheduler is always one replica, with strategy: Recreate. Two schedulers fire every schedule twice; and RollingUpdate starts the new pod before removing the old one, leaving a window with two alive.

Stateful stores run as StatefulSet + PVC, not Deployment: Postgres, Kafka, Qdrant and MinIO need a stable identity and a volume that reattaches to the same pod. On-prem means providing the storage layer yourself — k3s local-path, or Longhorn if volumes should be able to move between machines. This is the most labour-intensive part of leaving the cloud.

CI has no access to the cluster. It builds the image, pushes it to Harbor, then edits image.tag in git. Argo CD sees the git change and runs helm upgrade itself — the cluster credentials live in Argo, not in CI. Staging auto-syncs; prod needs a human, because deploying at 5pm on a Friday is not a machine's decision. Migrations still run first, via a pre-upgrade hook (Helm) or sync-wave -1 (Argo); if the hook fails everything stops and the old pods keep running.

4.4 · Status

What exists and what does not

This page describes a design, not a running system. The section below draws the line so nobody reads it the wrong way.

Item Status
Directory skeleton · layer conventions Built — the modules exist, docstrings state their responsibilities
docker compose · observability Config written: postgres, kafka, qdrant, minio, otel-collector, tempo, prometheus, loki, promtail, grafana
CI · build image Workflows exist: lint, type check, migrations, tests; builds an image tagged by SHA
Helm chart · Argo CD · Harbor Only values, Application and the decision docs. No real manifests in templates/ yet, and no cluster to deploy to
sources/ — connector No provider runs for real yet. Slack/Gmail/Confluence are still intentions
etl/ · agents/ · reports/ No transform step or agent has been implemented
evals/ — golden set The skeleton and the merge-blocking rule exist, but no data pairs yet
Model local 3B The specific work it carries is undecided. With no real high-volume work, the local layer can be dropped entirely

Summary

Nine rules that do not bend

If only one part of this page sticks, make it this one.

  • One direction Data only flows raw → silver → gold. No layer reads back upwards.
  • Agents read gold only Agents never touch raw or silver. Gold is the only contract.
  • Adding a source does not change existing code A new provider = one file in sources/ + one config file.
  • Models are called only through llm/ No module imports a provider SDK directly. Switching models, adding a cache, setting a spend ceiling — one change.
  • Slow work goes on the queue The API does not wait for an LLM. Push to queue/, return a job id, retry on failure.
  • Changing a prompt means running the evals A worse report does not turn a test red. Only the golden set catches it.
  • Thin controllers, thick pipelines If api/ could be deleted entirely and scheduler would still produce reports, the layers are in the right place.
  • One image for every environment Built once, tagged by commit SHA. Only environment variables differ.
  • Module name = what it does No abbreviations, no abstraction layers built for a future that has not arrived.
