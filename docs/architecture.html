Phần 1

Ý tưởng

Dữ liệu từ nhiều nguồn rời rạc chảy một chiều qua bốn tầng, cuối cùng thành báo cáo. Hiểu phần này là hiểu cả hệ thống làm gì.

1.1 · Luồng dữ liệu

Dữ liệu chảy một chiều qua bốn tầng

Mỗi tầng chỉ đọc tầng ngay dưới nó và ghi lên tầng ngay trên. Không có đường tắt: agent không bao giờ chạm raw hay silver.

Đây là trục dữ liệu, không phải trục request. Luồng sources → raw → etl → silver → gold chạy nền theo lịch, tính bằng phút. Còn khi người dùng bấm nút, request đi theo một trục khác — controller → pipeline → service, tính bằng giây. Hai trục gặp nhau đúng một chỗ: ở gold. Phần 2 nói về trục request.

1.2 · Hợp đồng giữa các tầng

Vì sao giữ nguyên raw

Khi logic transform sai — và nó sẽ sai — ta chạy lại từ raw thay vì phải gọi lại provider. Provider có rate limit, có dữ liệu đã bị xoá, có API đổi schema. raw là bản sao ta kiểm soát được.

Phần 2

Luồng code

Một yêu cầu đi qua những tầng nào, tầng nào gọi tầng nào, và module nào được phép import module nào.

2.1 · Trách nhiệm từng tầng

Ai làm gì trong một request

HTTP không gọi thẳng service. Nó vào managers/ — mỗi miền nghiệp vụ một thư mục, bên trong có controller nhận request và pipeline ghép các service lại.

Tầng Được làm Không được làm
api/app.py Tạo app, gắn controller của từng manager, middleware, observability Chứa endpoint · chứa nghiệp vụ
managers/·/controller.py Nhận request, validate, gọi pipeline, trả response SQL · gọi LLM · if/else nghiệp vụ
managers/·/pipeline.py Định nghĩa thứ tự các bước, gọi lần lượt service Tự làm việc của service · biết mình được gọi từ HTTP hay cron
services/ Một việc đơn lẻ, làm xong một chuyện, dùng lại được ở nhiều pipeline Gọi service khác thành chuỗi — đó là việc của pipeline
etl/ agents/ reports/ Năng lực nặng: transform, suy luận, dựng artifact Đọc request HTTP · viết SQL tay
storage/ Mọi câu SQL, session, transaction Chứa quyết định nghiệp vụ

Pipeline khác service thế nào: pipeline là chuỗi, service là mắt xích. managers/report/pipeline.py gọi lần lượt permission → queue → gather → analyze → render. managers/sync/pipeline.py gọi fetch → transform → check. Service dùng lại được ở cả hai; bản thân nó không biết mình đang nằm trong chuỗi nào.

2.2 · Vòng đời một yêu cầu

Từ lúc bấm cho tới lúc có báo cáo

Sinh báo cáo mất vài phút và sẽ có lúc lỗi giữa chừng. Vì vậy API không tự chạy — nó đẩy việc vào hàng đợi rồi trả về ngay. Toàn bộ đường đi là một trace.

2.3 · Thứ tự phụ thuộc

Thứ tự phụ thuộc

Mũi tên đọc là “được import bởi”. Không có mũi tên nào đi ngược lên — nếu bạn thấy mình cần import ngược, thiết kế đã sai chỗ nào đó.

Phần 3

Cấu trúc thư mục

Mỗi folder một việc, nhìn tên là biết. Phần cuối đi sâu vào tầng AI — chỗ dễ làm sai nhất.

3.1 · Cấu trúc thư mục

Nhìn tên là biết việc

Module phẳng, một tầng. Khi một module phình to thì tách thành thư mục và giữ nguyên tên: sources/slack.py → sources/slack/{client,parser}.py. Không dựng sẵn tầng trừu tượng khi chưa có gì để bỏ vào.

Mã nguồn
src/mycel/
├─ core/ Config, logging, exception, kiểu dùng chung. Tầng đáy — không import module nào khác.
├─ storage/ Ba kho, ba loại dữ liệu. Mọi truy cập đi qua đây — không rải rác trong pipeline hay agent.
│ ├─ storage/postgres/ State giao dịch: engine, session, repository cho từng tầng raw · silver · gold. Mọi câu SQL nằm ở đây.
│ ├─ storage/vectors/ Tìm kiếm knowledge base bằng embedding (Qdrant). Nguồn embedding là gold, không phải raw. Quyền xem là filter của Qdrant, không lọc sau khi lấy top-k.
│ └─ storage/objects/ File lớn: PDF nguồn, báo cáo đã render (MinIO, S3 API). Postgres giữ metadata, bucket giữ nội dung. API trả presigned URL nên file không đi qua process API.
├─ sources/ Mỗi provider một file. Cùng interface: nhận khoảng thời gian, trả bản ghi thô, ghi xuống raw.
├─ etl/ Các bước transform raw → silver → gold. Chạy nền theo lịch — không phải chuỗi xử lý request. Mỗi bước idempotent.
├─ etl/checks/ Kiểm tra sau mỗi bước: thiếu cột, null bất thường, số đếm lệch. Fail thì dừng, không ghi lên tầng trên.
├─ llm/ Cổng duy nhất tới mọi model. router chọn local hay cloud, client là nơi duy nhất import SDK provider, cache tránh gọi lại, tokens/usage đếm trước và sau, budget chặn vượt trần.
├─ agents/ orchestrator điều phối; analyst · writer · reviewer mỗi agent một việc; tools/ là năng lực agent gọi được (query_gold cho câu có số liệu chính xác, search_docs cho câu mơ hồ); prompts/ tách khỏi code để sửa không cần deploy.
│ └─ agents/core/ Nền chung của riêng agents/, không dính nghiệp vụ: vòng lặp agent, streaming/, hooks (gắn trace · log usage · cộng budget), guards, integrations/mcp.
├─ queue/ Tầng job trên Kafka (broker chạy ngoài, KRaft mode). Kafka là log có thứ tự chứ không phải hàng đợi task, nên phải tự làm: retry bằng topic theo bậc jobs → jobs.retry.1m → jobs.retry.10m → jobs.dlq, đếm số lần retry trong header, nâng max.poll.interval.ms. Commit sau khi job xong ⇒ at-least-once ⇒ idempotency key là bắt buộc. Cửa vào là services/enqueue.py.
├─ managers/ Điểm vào, chia theo miền nghiệp vụ. Thêm một miền = thêm một thư mục, không đụng miền đang có.
│ ├─ managers/report/ Miền báo cáo: controller.py (endpoint HTTP) · pipeline.py (chuỗi nghiệp vụ) · schemas.py.
│ └─ managers/sync/ Miền đồng bộ: cùng ba file đó, cho luồng fetch → transform → check.
├─ services/ Mắt xích đơn lẻ, mỗi file một việc: permission, enqueue, fetch, transform, gather, analyze, render, check. Tên là động từ, không hậu tố _service. Dùng lại được ở nhiều pipeline.
├─ reports/ Dựng artifact cuối từ kết quả agent: văn bản, bảng số liệu, dashboard.
├─ scheduler/ Trả lời khi nào chạy. Gọi thẳng pipeline trong managers/ — đúng chỗ controller gọi, chỉ bỏ qua mắt xích HTTP.
├─ api/ Vỏ HTTP, mỏng nhất có thể. Endpoint nghiệp vụ nằm trong managers/, đây chỉ gom lại. Có xác thực — dữ liệu là Slack và Gmail nội bộ.
│ ├─ app.py Nơi ráp: tạo app, gắn controller của từng manager, middleware, observability. File duy nhất biết hệ thống có những miền nào. uvicorn trỏ vào đây.
│ ├─ middleware.py Chỉ request_id — tracing, CORS, lỗi, rate limit đều dùng đồ có sẵn. Viết pure ASGI, không BaseHTTPMiddleware (nó buffer response, nghẽn SSE).
│ ├─ dependencies.py Thứ controller khai qua Depends(): xác thực, session DB, phân trang. Xác thực ở đây chứ không ở middleware — vào được OpenAPI schema và mypy kiểm được.
│ └─ health.py /health/live cho policy restart container, /health/ready cho load balancer. Không thuộc miền nghiệp vụ nào.
└─ observability/ tracing dựng OTel + xuất OTLP, llm_trace gắn thuộc tính LLM lên span (Langfuse đọc được), logging in JSON ra stdout (Promtail gom về Loki), metrics cho Prometheus. Ba tín hiệu ba câu hỏi: metrics có đang hỏng không, trace hỏng ở đâu, log hỏng vì sao — nối được nhờ trace_id có ở cả ba. Không biết HTTP là gì, nên scheduler và queue cũng import được. Mọi tầng gọi vào đây.
Vận hành
.github/workflows/ CI chạy mọi PR; build image tag theo commit SHA khi vào main.
evals/ Golden set chấm chất lượng báo cáo. Đổi prompt hay đổi model mà điểm tụt là chặn merge.
deploy/ Config hạ tầng: otel/ (collector · Tempo · Prometheus · Loki · Promtail), grafana/, init Postgres, inference/ cho vLLM, envs/, và phần triển khai cụm: kubernetes/ · helm/ · argocd/ · registry/.
config/ Cấu hình theo môi trường và theo nguồn. Bí mật ở .env, không bao giờ ở đây.
migrations/ Alembic. Mỗi thay đổi schema là một revision, không sửa DB bằng tay.
docs/ Tài liệu thiết kế — bao gồm chính trang này.
tests/ Test code, cấu trúc soi gương src/mycel/. Chất lượng báo cáo do evals/ lo.
scripts/ Script vận hành chạy một lần. Không phải nơi để logic nghiệp vụ.

3.2 · Tầng AI

Local gánh số lượng, cloud lo suy luận

Mọi lượt gọi model đều đi qua llm/ — không module nào import thẳng SDK của provider. Nhờ vậy đổi model, thêm cache, đặt trần chi phí chỉ sửa một chỗ.

Phần 4

Chạy thật

Docker, theo dõi hệ thống, và đường từ máy dev lên cụm. Kèm ranh giới rõ giữa cái đã có và cái mới chỉ là thiết kế.

4.1 · Stack vận hành

Stack vận hành

Một lệnh docker compose up dựng cả app lẫn tầng theo dõi. Thêm --profile local-llm nếu muốn chạy model 3B ngay trên máy. Đây là stack của máy dev — lên cụm thì cùng image đó chạy qua Helm, xem mục sau.

api Cổng vào

Nhận yêu cầu báo cáo, trả kết quả đã sinh, health check cho load balancer.

scheduler Đồng hồ

Tới giờ thì đẩy việc vào hàng đợi. Không tự thực thi, nên chết không mất job.

worker Tay làm

Rút job ra chạy: sync, transform, sinh báo cáo. --scale worker=N, nhưng N vượt số partition thì pod thừa ngồi không.

kafka Hàng đợi job

KRaft mode, không cần Zookeeper. Số partition là trần của song song, tăng được nhưng không giảm.

qdrant Vector store

Tìm kiếm knowledge base bằng embedding. Tách khỏi Postgres để scale độc lập.

minio Object store

File lớn qua S3 API: PDF nguồn, báo cáo đã render. Đổi sang S3 thật chỉ là đổi endpoint.

vllm Model local

Tuỳ chọn, bật bằng profile local-llm. Không bật thì mọi lượt gọi đi cloud.

postgres Kho dữ liệu

Một database, ba schema. Volume tách rời để nâng cấp image không mất dữ liệu.

otel-collector Điểm gom

App chỉ gửi OTLP tới một chỗ; collector chia về Tempo và Prometheus.

tempo Lưu trace

Một yêu cầu báo cáo là một trace: từ HTTP, qua query gold, tới từng lượt gọi model.

prometheus Lưu metrics

Độ trễ sync, số bản ghi mỗi tầng, token và chi phí theo model, tỷ lệ job lỗi.

loki Lưu log

Trả lời hỏng vì sao: stack trace, payload provider trả về. Nối với trace nhờ trace_id.

promtail Gom log

Đọc stdout của container rồi đẩy sang Loki. App chỉ in JSON, không biết Loki tồn tại.

grafana Màn hình

Dashboard và datasource, provision từ deploy/grafana/ nên versioned theo code. Bấm từ metric sang trace, từ trace sang log.

4.2 · Từ máy dev tới cụm

Một image, ba môi trường

CI build image một lần, tag bằng commit SHA. Staging và prod kéo đúng image đó về chạy — không build lại, nên không có chuyện “máy tôi chạy được”.

Môi trường Dữ liệu Model Khác biệt
dev Máy cá nhân, dữ liệu thật hoặc mẫu vLLM local nếu có GPU Chạy từ source, hot reload
staging Ẩn danh Cloud, key hạn mức riêng Cùng image với prod, khác biến môi trường
prod Thật, postgres có backup Cloud, key production Chỉ deploy tag SHA đã qua staging

Ba môi trường chạy cùng một image. Mọi khác biệt nằm ở biến môi trường: chuỗi kết nối DB, API key, có bật vllm hay không. Secret luôn đọc từ env — không bao giờ nằm trong config/ đã commit.

4.3 · Trên cụm

Kubernetes on-premise

Toàn bộ hệ chạy trong nhà, không phụ thuộc dịch vụ cloud nào ngoài lượt gọi LLM cuối. docker-compose.yml là stack của máy dev; deploy/helm/ là stack của cụm. Hai file khác nhau nhưng cùng một image và cùng một bộ biến môi trường — không có nhánh if env == "prod" trong code.

Cần gì Dùng gì Chỗ dễ sai
API scale được Deployment.replicas — nhiều pod sau một Service —
Pod chết tự sống lại kubelet restart container; Deployment dựng lại pod mất hẳn Pod treo mà vẫn mở cổng thì K8s coi là khoẻ. Self-healing chỉ đúng khi probe đúng
Traffic tăng thì thêm pod HorizontalPodAutoscaler api theo CPU, nhưng worker phải theo consumer lag của Kafka — nó chờ I/O nên CPU thấp trong khi hàng đợi dồn
Service gọi nhau Service — một DNS name ổn định, load-balance sẵn —
Deploy tái lập được Helm — chart có version, cùng chart + values-prod.yaml ra cùng kết quả version là của chart, appVersion là commit SHA của image. Rollback chart không rollback code
Deploy tự động Argo CD — git là nguồn sự thật, Argo so cụm với git rồi kéo cho khớp prune xoá tài nguyên không còn trong git: một dòng values sai là mất PVC của Postgres
Ảnh container riêng Harbor — registry nội bộ, kèm quét CVE, ký ảnh, proxy cache Tag = commit SHA, không bao giờ latest: hai pod cùng manifest sẽ chạy hai code khác nhau

Ba probe, ba câu hỏi khác nhau. readinessProbe quyết định có nhận request (fail thì rút khỏi Service, pod vẫn sống), livenessProbe quyết định có restart, startupProbe hoãn hai cái kia lúc khởi động. Thiếu cái cuối thì vllm bị giết oan vì nạp model mất vài phút — và lặp mãi.

Trần cứng của worker: số pod chạy thật = min(replica, số partition). Topic 6 partition thì HPA đẩy lên 10 pod cũng chỉ 6 pod có việc, nên maxReplicas đặt bằng số partition. vllm thì không autoscale chút nào: mỗi pod giữ một GPU, không có GPU rảnh thì pod mới chỉ Pending.

scheduler luôn một replica, và strategy: Recreate. Hai scheduler thì mỗi lịch bắn hai lần; mà RollingUpdate dựng pod mới trước khi xoá pod cũ, tức là có một khoảng hai cái cùng sống.

Kho có state chạy dạng StatefulSet + PVC, không phải Deployment: Postgres, Kafka, Qdrant, MinIO cần danh tính ổn định và volume gắn lại đúng pod cũ. On-prem thì phải tự lo lớp storage — local-path của k3s, hoặc Longhorn nếu muốn volume sang được máy khác. Đây là phần tốn công nhất khi bỏ cloud.

CI không có quyền vào cụm. Nó build image, đẩy lên Harbor, rồi sửa image.tag trong git. Argo CD thấy git đổi thì tự helm upgrade — credential của cụm nằm ở Argo, không nằm trong CI. Staging tự sync; prod cần người bấm, vì deploy vào 5 giờ chiều thứ Sáu không phải việc của máy. Migration vẫn chạy trước, bằng pre-upgrade hook (Helm) hoặc sync-wave -1 (Argo); hook fail thì dừng, pod cũ vẫn chạy.

4.4 · Trạng thái

Cái gì đã có, cái gì chưa

Trang này mô tả thiết kế, không mô tả một hệ thống đang chạy. Phần dưới nói rõ ranh giới để không ai đọc nhầm.

Hạng mục Trạng thái
Khung thư mục · quy ước tầng Đã dựng — module có sẵn, docstring nói rõ trách nhiệm
docker compose · observability Đã viết config: postgres, kafka, qdrant, minio, otel-collector, tempo, prometheus, loki, promtail, grafana
CI · build image Đã có workflow: lint, kiểm kiểu, migration, test; build tag theo SHA

sources/ — connector Chưa có provider nào chạy thật. Slack/Gmail/Confluence mới là dự định
etl/ · agents/ · reports/ Chưa có bước transform hay agent nào được cài đặt
evals/ — golden set Có khung và luật chặn merge, chưa có cặp dữ liệu nào
Model local 3B Chưa chốt việc cụ thể nó gánh. Không có việc khối lượng lớn thật thì bỏ hẳn tầng local

Tóm tắt

Chín quy ước bất di bất dịch

Nếu chỉ nhớ một phần của trang này, nhớ phần này.

  • Một chiều Dữ liệu chỉ chảy raw → silver → gold. Không tầng nào đọc ngược lên.
  • Agent chỉ đọc gold Agent không bao giờ chạm raw hay silver. Gold là hợp đồng duy nhất.
  • Thêm nguồn không sửa code cũ Một provider mới = một file trong sources/ + một file config.
  • Gọi model chỉ qua llm/ Không module nào import thẳng SDK provider. Đổi model, thêm cache, đặt trần chi phí — sửa một chỗ.
  • Việc lâu thì vào hàng đợi API không chờ LLM chạy xong. Đẩy vào queue/, trả job id, retry được khi lỗi.
  • Đổi prompt phải chạy eval Báo cáo kém đi không làm test đỏ. Chỉ golden set bắt được.
