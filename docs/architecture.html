Mycel

A multi-agent system that assembles reports and dashboards from scattered data sources. Named after mycelium — the underground fungal network connecting a whole forest: running in the background, quietly gathering data, and only then surfacing as a report.

Part 1

The idea

Data from scattered sources flows one way through four layers and ends as a report. Understand this part and you understand what the system does.

1.1 · Data flow

Data flows one way through four layers

Each layer only reads the layer directly below it and writes to the one directly above. No shortcuts: agents never touch bronze or silver.

This is the data axis, not the request axis. The flow sources → bronze → etl → silver → gold runs in the background on a schedule, measured in minutes. When a user presses a button the request takes a different axis — route → domain → service, measured in seconds. The two meet in exactly one place: at gold. Part 2 covers the request axis.

1.2 · The contract between layers

Why bronze is kept untouched

With one source, silver and gold hold the same columns — etl/promote.py is the identity function until a second tracker gives it something to reconcile. When transform logic is wrong — and it will be — it can be re-run from bronze instead of calling the provider again. Providers have rate limits, deleted data, and APIs that change schema. bronze is the copy we control.

Part 2

Code flow

Which layers a request passes through, which layer calls which, and which module may import which.

2.1 · Each layer's responsibility

Who does what in a request

HTTP does not call services directly. A route in api/routes/ validates the request and hands it to a module in domains/, which chains services into the operation. Nothing below the route knows HTTP exists.

Layer May May not
api/app.py Create the app, mount each router, middleware, observability Hold endpoints · hold business logic
api/routes/·.py Receive the request, validate, call a domain, return the response SQL · call an LLM · business if/else
domains/·.py Define the order of the steps, calling services in turn Do a service's work · import a FastAPI type · know who called it
services/ One single job, done end to end, reusable across domains Chain other services together — that is the domain module's job
etl/ agents/ reports/ The heavy lifting: transforms, reasoning, artifact building Read the HTTP request · write SQL by hand
infra/ Every SQL statement, session and transaction Hold business decisions

How a domain module differs from a service: the domain is the chain, a service is a link. domains/report.py calls, in order, permission → enqueue → gather → analyze → render. domains/sync.py calls fetch → transform → check. Services are reused by both; a service itself does not know which chain it is in.

2.2 · The life of a request

From the button press to the finished report

Producing a report takes minutes and will sometimes fail halfway. So the API does not run it — it pushes the work onto the queue and returns immediately. The whole path is one trace.

2.3 · Who is calling

A cookie, and one row that can be deleted

The data is a team's own tracked work, so every request has to name a person. HTTP remembers nothing between requests, so the browser carries a token and the server keeps the matching row.

Decision Why
Argon2id, not bcrypt bcrypt truncates silently at 72 bytes, so a long passphrase is only ever its first 72 and nobody finds out.
An opaque token, not a JWT Revoking a JWT needs a server-side list of revoked ones — that list is app.session with extra steps. So it is that table without them, and logging out deletes the row.
Expiry checked on read The database holds expires_at and enforces nothing. A session one second past expiry has to read as gone before any sweeper runs.
HttpOnly · SameSite=Lax A token a page can read is a token a cross-site script can steal. Lax keeps it off cross-site POSTs, which is the CSRF defence this needs while every mutating call comes from the app's own pages.
Depends(current_user),
not middleware		 It reaches the OpenAPI schema and mypy checks it. A middleware that sets a request attribute does neither.

Every security decision is in services/auth.py — one file to read before trusting this, and one file to change when an answer stops being good enough. The route layer in api/routes/auth.py only turns those calls into HTTP.

Authorisation is a separate question and is deliberately unfinished. services/permission.py holds one function that always returns true: there is no membership table, and inventing one that always answers true would be the same rule with more code. What is already right is the call site — every route that reads one project's data asks it first, before touching gold, so the day a rule exists it is added in one place.

2.4 · Dependency order

Dependency order

Arrows read as “is imported by”. No arrow points back upwards — if you find yourself needing an upward import, the design is wrong somewhere.

Part 3

Directory layout

One job per folder, obvious from the name. The last section goes deep into the AI layer — the easiest place to get wrong.

3.1 · Directory layout

The name tells you the job

Modules are flat, one level deep. When a module outgrows a file it becomes a directory with the same name: sources/slack.py → sources/slack/{client,parser}.py. No abstraction layer is built before there is anything to put in it.

Source
src/mycel/
E1 · Foundation Models, agents, config, tracing. Knows how to build an agent and emit a span; knows nothing about what the product does.
├─ core/ Config, logging, exceptions, shared types. The bottom layer — imports no other module.
├─ llm/ The only gateway to any model. router picks local or cloud, client is the only place that imports a provider SDK, cache avoids repeat calls, tokens/usage count before and after, budget blocks going over the ceiling.
├─ mcp/ MCP client only: toolsets built from config/mcp/servers.yaml, declared servers and never discovery — a tool’s name and description go straight into the prompt, so the list of them belongs in a diff.
├─ agents/ Four peers, differing in capability rather than rank: orchestrator routes a request, researcher searches the web and reads the deployment’s mailbox over IMAP (headers only, via sources/gmail.py), analyst reads gold with run_sql and computes, summariser writes a project's progress. tools/ holds those capabilities — delegate.py wraps an agent under that agent's own name, because pydantic-ai has no way to hand an Agent to an Agent; prompts/ is kept out of the code so edits need no redeploy.
│ └─ agents/core/ The shared foundation for agents/ alone, with no business logic: the agent loop, streaming/, hooks (attach traces · log usage · add to budget), guards, integrations/mcp.
├─ observability/ tracing sets OTel up and exports OTLP, llm_trace attaches LLM attributes to spans (readable by Langfuse), logging prints JSON to stdout (Promtail ships it to Loki), metrics feeds Prometheus. Three signals, three questions: metrics is something broken, traces where, logs why — joined by trace_id appearing in all three. It knows nothing about HTTP, so scheduler and queue can import it too. Every layer calls into it.
E2 · Entrypoints The ways in. A route parses and authorises; a service answers inside the request, in SQL. Work that takes seconds is handed to E4.
├─ api/ The HTTP shell, as thin as possible. Endpoints live in api/routes/, and each one validates then calls a module in domains/. There is authentication — the data is internal Slack and Gmail.
│ ├─ api/app.py The assembly point: create the app, mount each router, middleware, observability. The only file that knows which domains exist. uvicorn --factory points here.
│ ├─ api/middleware.py Only request_id — tracing, CORS, errors and rate limiting all use what already exists. Written as pure ASGI, not BaseHTTPMiddleware (which buffers the response and blocks SSE).
│ ├─ api/dependencies.py What routes declare via Depends(): authentication, DB session, pagination. Authentication lives here rather than in middleware — it reaches the OpenAPI schema and mypy can check it.
│ └─ api/health.py /health/live for the container restart policy, /health/ready for the load balancer. Belongs to no business domain.
├─ services/ Single links, one job per file: auth, permission, enqueue, fetch, transform, gather, analyze, render, check, dashboard. Names are verbs with no _service suffix. Reusable across domains.
E3 · Data Everything that owns a table. Connectors fill bronze, the ETL lifts it to silver then gold, the scheduler decides when. Nothing here calls a model.
├─ sources/ One file per provider. Same interface: take a time range, return raw records, write to bronze.
├─ infra/ Three stores, three kinds of data. Every access goes through here — not scattered through domains and agents.
│ ├─ infra/postgres/ Transactional state: engine, session, a repository per bronze · silver · gold layer. Every SQL statement lives here.
│ ├─ infra/vectors/ Knowledge base search over embeddings (Qdrant). Embeddings come from gold, not bronze. View permissions are a Qdrant filter, not a post-filter after top-k.
│ └─ infra/objects/ Large files: source PDFs, rendered reports (MinIO, S3 API). Postgres holds the metadata, the bucket holds the content. The API returns a presigned URL so files never pass through the API process.
├─ etl/ The bronze → silver → gold transform steps. Scheduled background work — not the request-handling chain. Every step is idempotent.
│ └─ etl/checks/ Validation after each step: missing columns, unexpected nulls, row counts off. On failure it stops and does not write to the layer above.
├─ scheduler/ Answers when to run. Calls domains/ directly — the same place a route calls, just without the HTTP link.
E4 · Background Work that outlives the request that asked for it. A route hands over an id; domains/ is the whole of one such unit of work, queue/ moves it between processes.
├─ queue/ The job layer on top of RabbitMQ (the broker runs outside). A task queue, not an ordered log, so retry and dead-lettering are broker features: mycel.jobs → jobs, dead-lettering to mycel.jobs.dlx → jobs.retry (TTL, then back) and jobs.dlq (nothing consumes it). Ack after the job finishes ⇒ at-least-once ⇒ an idempotency key is mandatory. The way in is services/enqueue.py.
├─ events/ The run narration: one event per step, published to a Redis Stream so /events can replay it as SSE. Separate from logs — logs are for operators, these are for the person watching a report being written.
├─ domains/ The business chains, one module per domain, none of them aware of HTTP. Adding a domain = one module here and one under api/routes/, with existing domains untouched.
│ ├─ domains/report.py Request a report, read what became of it. Queues the job and reads the result back out of app.report.
│ ├─ domains/sync.py The fetch → transform → check flow, against Jira. Called by scheduler/ on a timer and by stack.sh sync by hand — never over HTTP.
│ ├─ domains/dashboard.py Counts for one project over one window, and the list of projects that have work in them. A query, so it answers inside the request rather than queueing.
│ └─ domains/threads.py Whose sidebar history this is. GET /conversations reads it, so the list follows a person to any browser — which is why it stopped living in localStorage.
├─ reports/ Builds the final artifacts from agent output: prose, data tables, dashboards.
└─ notify/ One-way outbound: Telegram messages and Google Calendar events. Both optional, and a failure here never fails the job that triggered it.
Operations
.github/workflows/ CI runs on every PR; builds an image tagged by commit SHA on main.
evals/ The golden set that scores report quality. A prompt or model change that drops the score blocks the merge.
deploy/ Infrastructure config: otel/ (collector · Tempo · Prometheus · Loki · Promtail), grafana/, Postgres init, inference/ for vLLM, envs/, and the cluster deployment side: kubernetes/ · helm/ · argocd/ · registry/.

tests/ Code tests, mirroring the structure of src/mycel/. Report quality is evals/’s job.
scripts/ One-off operational scripts. Not a place for business logic.

3.2 · The AI layer

Local carries the volume, cloud does the reasoning

Every model call goes through llm/ — no module imports a provider SDK directly. That way switching models, adding a cache or setting a spend ceiling is one change.

Part 4

Running for real

Docker, observability, and the path from dev machine to cluster. With a clear line between what exists and what is still only design.

4.1 · The operational stack

The operational stack

One docker compose up brings up both the app and the observability layer. Add --profile local-llm to run the 3B model on the machine itself. This is the dev machine stack — on a cluster the same image runs through Helm, see the next section.

api Front door

Takes report requests, returns finished results, health checks for the load balancer.

scheduler The clock

Pushes work onto the queue when the time comes. It does not execute anything, so its death loses no jobs.

worker The hands

Pulls jobs and runs them: syncs, transforms, report generation. --scale worker=N, but pods beyond the partition count sit idle.

kafka Job queue

KRaft mode, no Zookeeper. The partition count is the parallelism ceiling; it can be increased but not decreased.

qdrant Vector store

Knowledge base search over embeddings. Kept out of Postgres so it scales independently.

minio Object store

Large files over the S3 API: source PDFs, rendered reports. Moving to real S3 is just an endpoint change.

vllm Model local

Optional, enabled with the local-llm profile. Without it every call goes to the cloud.

postgres Data store

One database, four schemas — bronze · silver · gold · app. A separate volume so upgrading the image does not lose data.

otel-collector Collection point

The app sends OTLP to one place; the collector routes it to Tempo and Prometheus.

tempo Trace storage

One report request is one trace: from HTTP, through the gold query, down to each model call.

prometheus Metrics storage

Sync latency, record counts per layer, tokens and cost per model, job failure rate.

loki Log storage

Answers why it broke: stack traces, the payload the provider returned. Joined to traces by trace_id.

promtail Gom log

Reads container stdout and ships it to Loki. The app only prints JSON and does not know Loki exists.

grafana The screen

Dashboards and datasources, provisioned from deploy/grafana/ so they are versioned with the code. Click from a metric to a trace, from a trace to logs.

4.2 · From dev machine to cluster

One image, three environments

CI builds the image once, tagged by commit SHA. Staging and prod pull that exact image and run it — no rebuild, so there is no “works on my machine”.

Environment Data Model Difference
dev Personal machine, real or sample data local vLLM if there is a GPU Runs from source, hot reload
staging Anonymised Cloud, its own rate-limited key Same image as prod, different environment variables
prod Real, postgres with backups Cloud, key production Only deploys SHA tags that passed staging

All three environments run the same image. Every difference is an environment variable: the DB connection string, API keys, whether vllm is enabled. Secrets are always read from env — never from a committed config/.

4.3 · On the cluster

Kubernetes on-premise

The whole system runs in-house, with no dependency on a cloud service beyond the final LLM call. docker-compose.yml is the dev machine's stack; deploy/helm/ is the cluster's. Two different files, but the same image and the same set of environment variables — there is no if env == "prod" branch in the code.

Requirement Solution Easy to get wrong
The API can scale Deployment.replicas — many pods behind one Service —
A dead pod comes back kubelet restarts the container; the Deployment recreates a lost pod A hung pod with an open port looks healthy to K8s. Self-healing is only correct when the probes are
More traffic adds pods HorizontalPodAutoscaler api on CPU, but worker has to scale on queue depth — it waits on I/O, so CPU stays low while the queue backs up
Services can reach each other Service — one stable DNS name, load-balanced already —
Reproducible deploys Helm — a versioned chart; the same chart + values-prod.yaml gives the same result version is the chart's, appVersion is the image's commit SHA. Rolling back the chart does not roll back the code
Automated deploys Argo CD — git is the source of truth; Argo compares the cluster to git and pulls it into line prune deletes resources no longer in git: one wrong line in values loses Postgres's PVC
Private container images Harbor — an internal registry with CVE scanning, image signing and a proxy cache Tag = commit SHA, never latest: two pods with the same manifest would run different code

Three probes, three different questions. readinessProbe decides whether it takes requests (on failure it is pulled from the Service, the pod stays alive), livenessProbe decides whether it restarts, startupProbe delays the other two during boot. Without the last one vllm is killed unfairly because loading the model takes minutes — forever.

worker’s hard ceiling: actual running pods = min(replicas, partition count). With a 6-partition topic, an HPA pushing to 10 pods still leaves only 6 with work, so set maxReplicas to the partition count. vllm does not autoscale at all: each pod holds a GPU, and with none free a new pod only sits Pending.

scheduler is always one replica, with strategy: Recreate. Two schedulers fire every schedule twice; and RollingUpdate starts the new pod before removing the old one, leaving a window with two alive.

Stateful stores run as StatefulSet + PVC, not Deployment: Postgres, RabbitMQ, Qdrant and MinIO need a stable identity and a volume that reattaches to the same pod. On-prem means providing the storage layer yourself — k3s local-path, or Longhorn if volumes should be able to move between machines. This is the most labour-intensive part of leaving the cloud.

CI has no access to the cluster. It builds the image, pushes it to Harbor, then edits image.tag in git. Argo CD sees the git change and runs helm upgrade itself — the cluster credentials live in Argo, not in CI. Staging auto-syncs; prod needs a human, because deploying at 5pm on a Friday is not a machine's decision. Migrations still run first, via a pre-upgrade hook (Helm) or sync-wave -1 (Argo); if the hook fails everything stops and the old pods keep running.

Summary

Nine rules that do not bend

If only one part of this page sticks, make it this one.

  • One direction Data only flows bronze → silver → gold. No layer reads back upwards.
  • Agents read gold only Agents never touch bronze or silver. Gold is the only contract.
  • Adding a source does not change existing code A new provider = one file in sources/ + one config file.
  • Models are called only through llm/ No module imports a provider SDK directly. Switching models, adding a cache, setting a spend ceiling — one change.
  • Slow work goes on the queue The API does not wait for an LLM. Push to queue/, return a job id, retry on failure.
  • Changing a prompt means running the evals A worse report does not turn a test red. Only the golden set catches it.
  • Thin routes, thick domains If api/ could be deleted entirely and scheduler would still produce reports, the layers are in the right place.
  • One image for every environment Built once, tagged by commit SHA. Only environment variables differ.
  • Module name = what it does No abbreviations, no abstraction layers built for a future that has not arrived.
