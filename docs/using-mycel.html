Mycel how to use it architecture database stack readme

From sign-up to a progress report

Mycel turns the work already in your issue tracker into a report and a dashboard. Nothing is asked of anyone except the habit they already have: keep issues in Jira. This page walks the whole path, in order, and says what to check when a step does not do what it should.

What the system actually does

Nobody fills in a form and nobody learns a convention. People work their board as they already do. A scheduled sync pulls in what moved, an ETL normalises it, and two things read the result: a dashboard that counts, and an agent that writes a summary in words. Due dates go out to a calendar.

Reading is the default and writing is opt-in, twice over. A fresh deployment reads Jira and writes nothing: the write tools only appear where somebody has turned on JIRA_WRITE_ENABLED, and creating a project needs a second switch of its own because it is the one change that cannot be undone from here.

And nothing is written under a name that did not agree to it. Every write runs on the consent of whoever is asking, and nothing reaches Jira or your calendar until it has been read back to you in words and you have said yes.

Before anything: is the stack up?

scripts/stack.sh dev up      # containers, migrations, api, worker, scheduler
scripts/stack.sh dev status  # what is running, and the links

up is idempotent: it starts what is down and leaves what is up. What you want to see from status is every row running — especially worker. Without the worker POST /chat hands back a job id for work nobody ever picks up, which on screen looks exactly like a slow model.

If api says foreign, some other process is holding port 8000 — usually a uvicorn left over from an earlier session, serving older code with half the routes missing. status prints the pid and the command to end it. Kill it and run up again.

Create an account

Open the app

http://localhost:8000/app/login — or just /app, which sends you here when you are not signed in.

Choose “Create one”

The form is one form with two verbs: the link under the button switches it between signing in and registering. Registration is open — anyone who can reach the page can make an account, which is fine for a machine on your desk and is the first thing to change if this is ever put on the Internet.

Email and a password of at least 8 characters

The email is only an identifier; nothing is sent to it. The password is hashed with Argon2id and the plain text is never stored or logged.

You are already signed in

Registering logs you in, so there is no second form. A session cookie is set that lasts 14 days. It is HttpOnly, so the page itself cannot read it — which is the point: a token JavaScript can read is a token a script can steal.

Signing out is the icon at the bottom of the left rail, beside your email. It deletes the session row, so the cookie is dead everywhere, not merely forgotten by this browser.

Your history follows the account, not the browser. Every run is saved against your user, so signing in on another machine shows the same list. That is the reason there is a login at all.

To forget one, hover its row in the rail and click the bin. The runs underneath it go too — the delete cascades in the database, so nothing is left behind.

Connect Jira

Two halves. The first is one-time setup done outside the app; the second is a button each person clicks once. Skip the first if someone has already registered the app.

Register an OAuth app

developer.atlassian.com → Create → OAuth 2.0 integration. Under Authorization, add a callback URL that is exactly your PUBLIC_BASE_URL followed by /auth/jira/callback — Atlassian refuses the round if it differs by a character.

Put four values in .env

JIRA_BASE_URL=https://your-site.atlassian.net
JIRA_CLIENT_ID=…
JIRA_CLIENT_SECRET=…
TOKEN_ENCRYPTION_KEY=…        # Fernet key; see .env.example for the one-liner

TOKEN_ENCRYPTION_KEY is what every stored consent is encrypted with, so without it nobody can connect anything and the board stays unread. The project key itself lives in config/environments/, not here — it is not a secret.

Connect your own account

Account menu → Settings → Connect Jira. You land on Atlassian's own consent screen, agree, and come back. The first person to do this becomes the one every background sync runs on, and the panel says so.

There is no shared Jira token, and that is the point. Reading a board on one would be harmless; writing to one would not. A comment posted on a deployment token appears under the host's name whoever typed it, and Jira offers no way to correct the author of an event already written. So every call runs on somebody's own consent.

Everyone else connects too, and gets the same thing minus the sync role: what they ask Mycel to write carries their name.

If the person driving the sync leaves, the syncing stops silently. Their consent goes with their Atlassian account, every tick fails, and a dashboard that has stopped moving looks exactly like a quiet week. scripts/stack.sh doctor is what tells them apart — it names who is syncing and when they last succeeded. Somebody else connecting takes the role back on.

Work the board

Nothing new to learn. The more of Jira's own fields a ticket carries, the more the report and the dashboard can say about it:

Field on the ticketWhat it makes possible
assigneePer-person load, and who to ask about a blocked item.
original estimateHalf of the estimated-versus-spent gap.
time spentThe other half. Jira's running total on the ticket, which is what the per-person table reads.
work logThe only honest effort-per-day curve, because a work log carries the date the work was done for.
due dateWhat is at risk, and what lands on the calendar.
parent (epic)Progress grouped at the level a plan is discussed at.

Log hours against the day they were worked. Jira lets a worklog carry its own started date, and that is the one time field that can be back-dated honestly. Created dates and status transitions are stamped by Jira with the moment of the API call, so on a back-filled project they are a confident lie — which is why Mycel draws effort from worklogs and never draws "issues resolved per day" at all.

Pull the work in

The scheduler does this every 15 minutes on its own. To see a change immediately, run one sync by hand:

scripts/stack.sh sync

It prints how many issues it pulled. A sync only asks for what moved — the JQL carries updated >= the last high-water mark — so a quiet quarter of an hour legitimately pulls zero. Zero when something did move means one of two things, in the order worth checking:

  • The account the token belongs to cannot see that project. The sync sees exactly what that person sees when they log in.
  • The token expired. One year, silently. The log line says 401.

Read the numbers

Ask for them. /app takes “what is late right now” or “compare hours logged this month with last” and the analyst writes its own SQL against the work data, returning each figure with the query that produced it. There used to be a dashboard page that answered in milliseconds and could only answer the six questions it was built for.

The six are worth knowing anyway, because they are the ones that are easy to read under the wrong scope. Whole-project and window are different questions, and a count is wrong rather than merely imprecise when the two are mixed — a percentage drawn from a 7-day count reads a quiet week, two tickets moved and one done, as a project half finished. Say which you mean in the question.

Ask aboutWhat it counts, and over what range
progressThe whole project: items done over items that exist, 0-100. The one figure on the page that is not the window, which is why it is drawn above the divider and says so.
work touchedItems changed in the window, counted by the status category they are in now — not how many moved into it. Jira's own categories, so two sites with different workflow names still compare. Every issue type counts as one, epics included.
past dueThe whole project, not the window: due date in the past and not done, most overdue first. A ticket overdue since last month that nobody has touched since is the one most worth seeing, and a window is exactly what hides it.
per personThe window picks which tickets; the estimate and spent on them are Jira's running totals for the ticket's whole life, in man-days at its eight-hour day. Gap is spent minus estimated — positive means over. An estimate of zero means the tickets carry none, not that the work was free.
epicsOne bar per epic, drawn from the epic's whole size — that is what makes two epics comparable. Under each bar, moved is how many of its children changed in the window; a zero there is an epic nobody has touched lately, which is worth seeing next to how far along it is. Every epic in the project appears, including ones nothing moved under. The epic itself is never counted among its own children.
effort loggedHours from work logs, on the day the work was logged for. The only block measuring effort inside the window, so it does not add up to the spent column above. Not issues resolved per day — see the note in step 04.

Progress and the epic bars are the whole project, and so is past due; the other three are the window. Each block says so on screen, because a count read under the wrong scope is worse than no count.

Two kinds of "spent" on one page, and they are allowed to differ. Per person sums what Jira holds on the tickets the window selected — running totals for each ticket's whole life. Effort logged sums the work logs dated inside the window. A ticket opened in June and touched yesterday puts every June hour in the first and none in the second. Neither is wrong; they answer different questions.

A project with no data is an empty answer, not an error: a project that has been set up and has not synced yet is a normal state and the agent says so rather than inventing a number.

Ask for a progress summary

Ask for one: “how is MYC going this week”. The orchestrator hands it to the summariser, which takes the project key and the window out of your sentence. There used to be a form for this, with a project picker and a day count; a sentence carries both and does not have to be found first.

It comes back immediately with a job id

That is a receipt, not an answer: a run takes minutes and every proxy in front of the API would time out waiting. The work happens in the worker process.

The run streams as it happens

Reasoning, tool calls, and work delegated to other agents nested under the call that asked for it. If the connection drops the browser resumes rather than replays.

The summary arrives at the end

It is read top-down. A verdict — on track, at risk, or off track — then a one-sentence headline, then the counts, then the lists. A reader who stops after two seconds has still been answered; everything below is the evidence for those three lines.

The lists are tables, not bullet points: issue, title, epic, who, estimate, spent and due. The last three are what a standup argues about — without them the table says what moved without saying whether it moved on time. An empty cell means the ticket carries no estimate or no due date, which is not the same as a zero. What is at risk sits above what shipped on purpose — highlights are the pleasant part of a standup and the part nobody has to act on. An empty At risk table is the answer, so it is shown rather than hidden. Per person is its own table: items, done, estimated, spent.

The model fills columns, not sentences. Each row is a set of fields — key, title, epic, who — and a note only where the row needs a reason to be read. When those were one string per line, every surface that wanted a table had to split the model's prose back apart on a dash, and a dash can appear inside a ticket title. A column the model fills is a column a renderer can align.

The prompt side is the same idea. Each work item reaches the model as named fields — key= status= kind= title= who= estimated= spent= due= — with the same names its output row has, so copying is matching a label rather than counting a position. The first version wrote the kind immediately before the title and got back titles reading story: 003 — API skeleton. A field the ticket does not carry is left off the line entirely, which is how the model learns that missing and zero are different.

The verdict is judged, not computed. A threshold in code gives one rule — "anything overdue is at risk" — and a project with a single ticket two days late stays amber forever. The model has the whole window in front of it and can tell "late but moving" from "late and stopped". Every number on the page is still SQL; only the verdict is the model's.

The summary does not come down the stream. The agent's output is structured and is handed back separately, which is why the page keeps polling for a moment after the events stop.

It is still there tomorrow. Every run is written twice — to Redis, which knows a run is still in flight and forgets it after an hour, and to Postgres, which is the record. Reopening a thread from the rail next week reads the second one.

Your calendar, in the same box

Optional, and per person. Nobody's calendar is touched until they have been through Google's own consent screen, and a deployment with no OAuth client says so rather than offering a button that leads to an error.

Set up the client, once

GOOGLE_CLIENT_ID=…apps.googleusercontent.com
GOOGLE_CLIENT_SECRET=…
TOKEN_ENCRYPTION_KEY=…

In the Google Cloud console: Credentials → Create credentials → OAuth client ID → Web application, and under authorised redirect URIs add exactly your PUBLIC_BASE_URL followed by /auth/google/callback. Google matches that string character for character, and a mismatch is the one error everybody hits first. Enable the Google Calendar API for the same project.

The token key is Fernet, and it is what keeps the stored consent secret:

python -c "from cryptography.fernet import Fernet; print(Fernet.generate_key().decode())"

A refresh token opens one person's calendar until they revoke it, so it is encrypted before it reaches the database and never appears in a log line or a prompt. A deployment with a client and no key counts as not configured — refusing is better than storing one readably. Rotating the key disconnects everybody, who fix it by connecting again.

Connect an account

Account menu → Settings → Connect Google Calendar. The consent screen is Google's; what comes back is permission to read that one calendar and add events to it. The scope cannot delete a calendar, and nothing in Mycel deletes or edits an event — changing a booking happens in Google, where you can see the week you are changing.

Disconnect on the same screen revokes it at Google and forgets it here.

Ask, and book in one sentence

“What have I got this afternoon?” reads the window and answers with each event's own link. “Book the review, 3pm tomorrow, half an hour” does not book anything: it reads the time back to you in words — Friday 2 October 2026, 15:00 — and waits. Only your yes writes to the calendar.

That split is deliberate. A time is something the model read out of a sentence, and a wrong reading that reaches Google puts a meeting nobody arranged on a real phone. A proposal you can correct costs one turn; a ghost meeting costs an afternoon.

Answers use the timezone in TIMEZONE, in both directions, so a server in UTC does not book your three o'clock seven hours early.

One box, four specialists

/app is the whole app. Ask a question in plain language; an orchestrator reads it and delegates. There is nowhere else to go, which is the point — you no longer have to know which page a question belongs to before you can ask it.

Ask thisWhat answers it
“how is MYC going this week”The summariser, on the window you named in the question.
“what is late right now, and who is it with”The analyst, the question the dashboard page used to answer.
“who logged the most hours this month”The analyst, which writes its own SQL against the work data and returns each figure with the query that produced it.
“comment on MYC-12 that it is done”The analyst, where the deployment allows writing. It reads the change back first and writes nothing until you agree — then the comment appears on Jira under your name.
“create a task for the login timeout, assign it to Nam”The analyst again. It looks Nam up by name, reads the whole ticket back — type, project, title, the assignee’s full name — and waits. Two people called Nam both come back, and it asks which.
“what changed in Jira’s API this year”The researcher, which searches the web and cites urls.
“anything important in the mail today”The researcher again. It reads the sender, subject and date of messages from the last 24 hours — a week or a month if that is what you ask for — and links each one. Bodies are never read, so it says when a subject line is not enough to be sure.

The answer suggests what to ask next. Under it sit up to three questions the run itself wrote, from what it just found — a figure worth breaking down, a gap it had to record. They come back with the answer rather than from a second call, so they cost nothing and are about your answer rather than a fixed menu. Clicking one fills the box; you still press Enter. An answer that closes its subject suggests nothing, which is why the row is sometimes not there.

Nothing scrolls the page but you. The view stays where you put it — while the work runs, and when the answer lands. The answer often arrives while you are reading the step that produced it, and being thrown to the bottom there is the same interruption as being thrown there by a tool call. When the bottom is off screen a small arrow appears; going down is a click.

Reading that data is read-only and enforced as such by Postgres, not only asked for in a prompt: run_sql runs inside a read-only transaction, so a question that would change anything is refused by the database and the agent says so. Changing the tracker does not go through there at all — it goes to Jira, on your consent, after a read-back.

What the deletion cost. The dashboard answered in milliseconds and for free; the same question now costs a model call and a few seconds, against a free tier of 20 requests a day. That was traded deliberately for not having to know which page holds which answer. If the cost bites, the fix is a higher tier or a cached window — not a second screen.

When something looks wrong

What you seeWhat it usually is
Login page on every reloadThe cookie was cleared, or 14 days passed. Sign in again.
Empty project dropdownNothing has synced yet. scripts/stack.sh sync, then check its log line.
Sync pulls zero issuesA project the token's account cannot see, or a token that turned one year old.
Estimated is zero for everyoneThe tickets carry no original estimate. Mycel reports the field, it does not invent it.
Effort chart is flat, work is clearly happeningNobody is logging work. The curve comes from work logs and from nothing else.
Calendar events never appearThe calendar is not shared with the service account's email address.
A run is queued and never movesThe worker is not running. scripts/stack.sh dev status, then dev logs worker.
A run fails part-wayUsually the model provider — a free-tier quota or a missing key in .env. The failure reason is shown on the run.
api reads foreignA stale process on port 8000. status prints the pid and the command.
