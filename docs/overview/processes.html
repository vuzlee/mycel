Mycel handbook / Overview / Processes

Four processes, one image

The same code runs as four programs. Each does one kind of work, so a slow model answer never blocks a page load and a crash loses no question.

01 · The four

What each process consumes, and how many may run.

apiAnswers HTTP

Routes, sign-in, the web app at /app, event streams. Writes jobs; never runs a model.

uvicorn --factory mycel.api.app:create_app · replicas: any

workerRuns chat jobs

Consumes queue jobs, 2 at a time. Runs the agents, stores the answer.

python -m mycel.worker · replicas: 2

ingestParses and embeds

Consumes queue ingest, 1 at a time. Restarts itself after 20 jobs to give memory back.

python -m mycel.worker --queue ingest · replicas: 1

schedulerKeeps time

Timers: outbox relay, one sync per plugin, sweeps, queue gauges.

python -m mycel.scheduler · replicas: 1, Recreate

Key insight: ingest is a separate process because parsing a PDF can take gigabytes; a chat worker next to it would be killed with it.

Details
  • Dev: scripts/dev/up.sh runs all four on the host; ingest under scripts/dev/ingest-loop.sh, capped at INGEST_MEM (4G) and INGEST_CPUS (2).
  • Compose: the ingest service has its own image target (ingest), mem_limit: 5g.
  • The scheduler is Recreate: a rolling update would run two for a moment. Its per-timer lock would still stop doubles, but a tick would be skipped.

02 · Start and stop

Every process opens the same way and closes the same stores in the same order.

Key insight: lifecycle.py is shared by all four, so a new store needs one closer in one list, not four shutdown paths.

Details
  • The api does not call start(): create_app sets up logging and tracing itself, then lifespan uses running("api").
  • /metrics port = METRICS_PORT (9100) + offset: worker 0, scheduler 1, ingest 2, api 3.

03 · A job in the worker

The worker reads the job's kind, runs that domain, and sorts any failure into one of three bins.

Key insight: only failures that can pass on their own are retried; a model that refused, or a loop the guard stopped, goes straight to the dead-letter queue.

Details
  • Lists: FINAL and TRANSIENT in worker.py; settling in queue/consumer.py.
  • A body that will not parse is dead-lettered with nothing recorded: there is no turn to record it on.
  • Retries, the dead-letter queue and replay: Retry, DLQ, replay. Running a job once: Idempotency.

04 · Scheduler timers

05 · When things go wrong

Worker gets SIGTERM
stops taking jobs→waits up to 50 s for running ones→the rest are redelivered
Worker killed outright
unacked jobs redelivered→too many deliveries → dead-letter
A timer tick fails
logged→next tick runs as usual
Scheduler stops
ticks in progress are cancelled, not finished
One store fails to close
warning→the others still close

06 · Guaranteed / not guaranteed

Guaranteed

  • A job a worker did not ack is delivered again
  • One timer tick at a time across replicas
  • Every store is closed on a clean stop

Not guaranteed

  • A job cut short finishes: it starts again from the beginning
  • A scheduler tick that was cancelled runs again before its next interval
